## Meteor Key & Evaluator (exact semantics)

```text
request key:    key.meteor-client.open-gui
fallback key:   [[NO_METEOR_CLIENT]] (auto-generated: no explicit fallback configured)
mode:           METEOR
transport line: Component.translatable(key, fallback) on a server sign,
                resolved client-side, read back via SignChangeEvent
```

Evaluator (`CheckHacksResponseEvaluator.evaluate`, CheckHacks 1.3.1 branches):

```text
outcome TIMEOUT                       -> PROTECTED (never CLEAN)
outcome DISCONNECTED | ERROR          -> ERROR    (never CLEAN)
RESPONSE empty/null line              -> CLEAN
RESPONSE key + 1 trailing letter      -> CLEAN (near-miss guard)
RESPONSE == fallback prefix           -> CLEAN (vanilla path)
RESPONSE == key exactly               -> DETECTED
RESPONSE anything else                -> DETECTED
```

Vanilla client behavior: returns the fallback, so `meteor-client` evaluates
`CLEAN`. A client resolving the key to any other text evaluates `DETECTED`
(initial), then the flagged probe is re-run as `CONFIRMATION`; only
`CONFIRMATION + DETECTED` can produce a confirmed positive and a kick.

Consequence for Player C: if the installed Meteor build does not register
`key.meteor-client.open-gui` (renamed key, fork, version drift), the client
returns the fallback exactly like vanilla and the probe is indistinguishable
from clean. The key is `UNVERIFIED` against any pinned Meteor release, so
this is the leading hypothesis — but without a recorded response it remains
a hypothesis, not a verdict.
